* 1. **Python / function APIs:** `_result()` accepted optional parameters positionally, so calls that passed `started` immediately after `compile_stage` accidentally assigned the `time.monotonic()` float to `test_stage`; make optional stage/timing arguments keyword-only and call them explicitly as `started=started`, `test_stage=test_stage`.
* 2. **Python dataclasses / serialization:** `GraderResult.to_record()` assumed `test_stage` was an `ExecutionStageResult` and called `.to_record()`, but the positional-argument bug made it a float and caused `AttributeError: 'float' object has no attribute 'to_record'`; strongly type internal objects, use keyword-only APIs, and regression-test serialization on every exit path.
* 3. **Regression harness:** A serialization exception was converted into `HARNESS_ERROR`, making all 11 deterministic cases initially appear broken for the same infrastructure reason and hiding their actual grader outcomes; treat `HARNESS_ERROR` as infrastructure failure rather than model correctness.
* 4. **Regression metrics:** `0/11` when every case is `HARNESS_ERROR` is not meaningfully a 0% model/candidate score because an infrastructure outage can look like catastrophic model regression; report harness health separately from task correctness.
* 5. **Python / grader control flow:** Compile-time `_result(...)` branches contained the positional bug while some later test-stage calls happened to be positionally correct, so the defect mainly appeared on early-return/error paths; test every failure branch instead of only the happy path.
* 6. **Unit testing / FakeExecutor:** Grader unit tests used a `FakeExecutor`, allowing Python logic to remain completely green while real Docker integration was broken in several different ways; keep fake-executor tests but add real sandbox smoke/integration tests.
* 7. **pytest / Bash heredocs:** A shell command was accidentally appended literally to `ml/tests/test_grader.py` as `PYcd /home/projects/Cortexo && cat >> ...`, causing pytest collection to fail with a Python `SyntaxError`; heredoc terminators such as `PY` must be alone on their line and modified tests should be syntax-checked before running the suite.
* 8. **Bash / heredocs:** Concatenating a heredoc terminator with the next command turns that following shell text into source code, which is exactly how the `PYcd ...` corruption occurred; never place another command on the heredoc terminator line.
* 9. **Bash / interactive shells:** A diagnostic command ended with `exit "$RC"`, so pasting it into an interactive terminal closed the user's shell; copy-paste diagnostics should run in a subshell, capture and print the RC, and finish with `true` rather than `exit`.
* 10. **Bash / pipelines:** With `command | tee logfile`, ordinary `$?` reports the exit status of the last pipeline command such as `tee` rather than necessarily the program being tested; use `PIPESTATUS` to capture the intended command's exit code.
* 11. **Bash / diagnostics:** Large `&&` or `set -e` chains can stop at the first failure and suppress the useful diagnostics needed to understand later layers; diagnostic scripts should use `set +e`, capture exit codes explicitly, and preserve failed logs/workspaces.
* 12. **Docker CLI:** The sandbox used `-m` as though it represented milliseconds or a timeout, but Docker's `-m` option actually means memory; never use Docker `-m` for execution timeouts.
* 13. **Docker memory limits:** The runner already supplied `--memory 1g` and then appended `-m 60000` intending a 60-second timeout, effectively replacing the intended 1 GB limit with roughly 60 KB and causing containers to fail before meaningful compilation; keep memory configuration separate from timeout configuration.
* 14. **Docker / timeouts:** Docker did not require the fake `-m` timeout because Cortexo already had `/usr/bin/timeout --kill-after=10` plus a host-side `communicate()` timeout/kill path; use those actual timeout mechanisms and keep them independent from memory limits.
* 15. **Docker `--cidfile`:** The runner used `tempfile.NamedTemporaryFile(delete=False)` as the path for `docker run --cidfile`, but Docker requires that CID file not to exist beforehand and therefore failed with exit code `125` and `container ID file found`; reserve a temporary directory and pass Docker a nonexistent child path such as `container.cid`.
* 16. **Python tempfile + Docker:** Creating a temporary filename and reserving a path that Docker itself must create are different operations because `NamedTemporaryFile` immediately creates the file; use `mkdtemp()` for the parent directory and let Docker create the CID file.
* 17. **Docker process classification:** Docker startup failures such as exit `125` or `127` occurred during the nominal COMPILE stage and were therefore reported as `COMPILE_FAIL` even though Python compilation never started; classify runner/container startup failures separately from genuine compiler failures.
* 18. **Regression classification:** `merge-dicts-syntax-error` temporarily passed because its expected status was `COMPILE_FAIL` and broken Docker infrastructure also produced `COMPILE_FAIL`, resulting in an accidental `1/11`; an expected status match is insufficient when infrastructure health is bad.
* 19. **Regression deltas:** The syntax-error case produced an apparent positive delta when broken infrastructure began matching its expected `COMPILE_FAIL`, making quality look improved when it was only an infrastructure-correlated false positive; interpret regression deltas only when the execution layer is healthy.
* 20. **Docker / seccomp / runc:** Cortexo used a hand-written `SCMP_ACT_ERRNO` syscall allow-list that omitted syscalls required by modern `runc`, causing the container to fail before candidate execution; recognize that manually maintained syscall allow-lists carry runtime-version compatibility costs.
* 21. **Linux syscalls / runc:** The custom seccomp profile omitted `fstatfs` and `statfs`, causing container startup to fail around `/proc/thread-self/fd` with `fstatfs ... operation not permitted`; either carefully maintain all legitimate runtime syscalls or prefer Docker's maintained default seccomp profile.
* 22. **Linux syscall compatibility:** Adding `fstatfs` and `statfs` merely advanced startup to the next failure, `Fatal glibc error: Cannot allocate TLS block`; repeatedly adding individual syscalls is a brittle long-term sandbox maintenance strategy.
* 23. **glibc / x86-64 / seccomp:** The custom seccomp profile also lacked `arch_prctl`, strongly indicating why glibc TLS initialization could not complete; runtime and libc initialization depend on architecture-specific syscalls that an application-centric allow-list can easily miss.
* 24. **Docker security:** Removing Cortexo's custom seccomp override does not mean using `seccomp=unconfined`; without the override Docker automatically applies its maintained default seccomp policy, which is preferable here to disabling seccomp.
* 25. **Sandbox security:** Seccomp is only one sandbox boundary, so after removing the custom profile the system must still preserve `--network none`, `--read-only`, memory/CPU/PID limits, a non-root UID, `--cap-drop ALL`, `no-new-privileges`, timeouts, and no Docker socket.
* 26. **Custom seccomp security:** The old home-grown allow-list simultaneously blocked harmless runtime operations while unconditionally allowing sensitive calls such as `ptrace`, `process_vm_readv`, and `process_vm_writev`; a custom profile can be both too restrictive and too permissive, so maintained profiles are generally safer than casually expanding one.
* 27. **Docker vs host filesystem permissions:** Once Docker's default seccomp profile allowed execution to reach Python, the next failure became a filesystem permission problem, proving Docker/runc itself was functioning; debug individual layers independently instead of changing several security controls at once.
* 28. **Python `compileall`:** `compileall` writes `.pyc` files, so a readable but non-writable source tree produced `PermissionError` on `./__pycache__`; compilation requires a writable bytecode destination even when source is deliberately immutable.
* 29. **Python environment variables:** `PYTHONDONTWRITEBYTECODE=1` did not fix the problem because `compileall` explicitly requests bytecode generation rather than relying on normal import caching behavior; redirect bytecode with `PYTHONPYCACHEPREFIX=/tmp/pycache`.
* 30. **Docker tmpfs / Python:** `/tmp` was already configured as writable tmpfs, providing a safe writable location for generated bytecode without making `/work` writable; use `/tmp/pycache` for Python cache output.
* 31. **Linux permissions / Python tempfile:** `tempfile.mkdtemp(prefix="cortexo-grader-")` creates the grader workspace with mode `0700`, meaning only the host owner can traverse it; account for this default when bind-mounting the directory into a container running under another UID.
* 32. **Docker non-root user / Linux UID:** The sandbox intentionally runs as `--user 10001:10001`, but UID 10001 is not the host owner of the `0700` grader workspace and therefore cannot traverse `/work`; host/container UID boundaries still apply to bind-mounted filesystem permissions.
* 33. **Docker bind mounts:** Bind-mounting a host directory into `/work` does not bypass the host directory's Unix mode bits, so UID 10001 could have the mount present while remaining unable to see its contents; mounted directories must be traversable by the container UID.
* 34. **Sandbox workspace permissions:** Manual smoke tests succeeded after `chmod 755 "$WS"` while the actual grader did not perform the same chmod, causing manual and production execution paths to behave differently; configure the real grader workspace with the permissions genuinely required by the sandbox.
* 35. **Least-privilege filesystem design:** The correct workspace permission fix is not `chmod 777`, because giving untrusted candidate code arbitrary host-bind-mount write access weakens the sandbox; use directory mode `0755` for traversal while keeping candidate and hidden-test files non-writable.
* 36. **Grader architecture:** Candidate modifications are applied on the trusted host before sandbox execution, so untrusted code does not need write access to source files merely to be evaluated; keep `/work` effectively read-only to UID 10001 and direct runtime scratch state to `/tmp`.
* 37. **pytest discovery:** Hidden tests were correctly named `test_*.py` and copied under `benches_hidden/`, so `NO_TESTS` was not actually a naming/discovery-definition problem; verify filesystem visibility before changing pytest configuration or test names.
* 38. **pytest / permissions:** pytest returned zero collected tests because the sandbox could not traverse the grader workspace, meaning `NO_TESTS` did not mean the registry contained no tests; zero-test collection can be caused by environment and access failures.
* 39. **Python `compileall` / permissions:** The inaccessible workspace also made compilation appear successful because the compiler effectively saw nothing useful to compile; a zero-error compiler invocation does not prove the intended source files were visible.
* 40. **Regression semantics:** After fixing Docker, every case becoming `NO_TESTS` changed the numerical result from accidental `1/11` to `0/11`, but this was actual progress because execution had advanced into pytest; evaluate the failure layer and status meaning rather than only the numeric score.
* 41. **Regression harness:** `TEST_FAIL` and `COMPILE_FAIL` both imply `passed=False` but represent different failure reasons, so checking only pass/fail can count the wrong failure as correct; require both `expectedStatus` and `expectedPassed` to match.
* 42. **Regression harness resilience:** A single harness exception should not terminate the entire suite because continuing provides enough evidence to spot patterns such as 11 identical failures; convert per-case exceptions into `HARNESS_ERROR`, continue running remaining cases, and fail the overall gate.
* 43. **Test strategy:** The Python suite grew from 82 to 84 to 87 passing tests while end-to-end regression remained broken, showing that unit-test count alone created false confidence; full-stack deterministic regression covers materially different behavior from unit testing.
* 44. **Test counts:** Exact total test counts changed as regression coverage was added, so permanently asserting that there must always be exactly 84, 87, or another fixed count would be brittle; assert required behavior and capabilities rather than a permanent global test count.
* 45. **Docker image build:** `docker build` produced a legacy-builder deprecation warning that looked noisy but was unrelated to the actual failures; distinguish warnings and deprecations from commands that truly return a nonzero failure.
* 46. **Make / working directory:** `make regression` runs `cd ml && .venv/bin/python ../scripts/run_regression.py --mode full`, making the changed CWD a plausible initial suspect but not evidence of the actual bug; inspect concrete errors before rewriting working-directory logic.
* 47. **Python subprocess / paths:** `SandboxExecutor` deliberately invokes the sandbox runner with `cwd=self.repo_root`, making the earlier hypothesis that `cd ml` was breaking relative sandbox paths less likely; trace actual subprocess CWD and path resolution before changing Make targets.
* 48. **Debugging discipline:** The initial CWD hypothesis became obsolete once the report exposed `'float' object has no attribute 'to_record'`; direct new evidence should supersede older guesses rather than allowing debugging to continue down an outdated path.
* 49. **Regression reports:** `Dirty working tree: True` appeared throughout because fixes were still uncommitted, but it was report metadata rather than a regression failure; do not treat a dirty tree as gate failure unless policy explicitly requires a clean repository.
* 50. **Generated regression reports / Git:** `artifacts/evaluations/regression/*` contains generated output, and committing it would pollute source control and confuse historical deltas; Git-ignore generated regression reports.
* 51. **Git / evaluation baselines:** `benchmarks/baselines/**` contains deterministic known-good and known-bad evaluation inputs, and ignoring it would make CI unable to reproduce the suite; baseline material should remain tracked in Git.
* 52. **LLM training / data leakage:** Some deterministic baseline candidates are literal known-good answers, so training on them would contaminate the benchmark and invalidate evaluation; explicitly exclude `benchmarks/baselines/**` from training ingestion.
* 53. **LLM evaluation / hidden-test leakage:** Hidden tests contain evaluator-only information, and exposing them to training or model-visible context turns evaluation into leakage; exclude `benchmarks/hidden_tests/**` from both training and model-visible retrieval/context.
* 54. **Grader ordering / LLM evaluation:** Hidden tests must be staged only after model generation because staging them earlier gives an agent an opportunity to inspect evaluator-only information; use the order generation → candidate application → hidden-test staging → sandbox execution.
* 55. **Gold patches / LLM leakage:** Gold patches and known solutions must never be substituted into candidate code or model-visible prompts because that would manufacture a fake successful evaluation; keep gold fields evaluator-only and scan code for accidental assignments or exposure.
* 56. **Baseline manifest security:** A deterministic baseline manifest should contain case data rather than arbitrary executable machinery because fields such as `command`, `argv`, or `testCommand` would turn data into an RCE configuration surface; strictly allow known manifest fields and keep execution configuration trusted in grader code.
* 57. **Path traversal / regression manifests:** Candidate paths supplied through manifests become dangerous when accepted blindly because `../` or absolute paths could escape the baseline directory; resolve each path and require it to remain underneath `benchmarks/baselines/`.
* 58. **Evaluation integrity:** Regression infrastructure must never automatically update expected values to match whatever the current implementation produces because a bug could rewrite its own benchmark until it passes; expectations are curated source data and should change only through explicit review.
* 59. **Canonical task data:** Hidden evaluator metadata should come from canonical task/registry files rather than being duplicated into public baseline manifests because duplication can drift and leak evaluator details; manifests should identify a canonical `taskId` and let the trusted grader load canonical data separately.
* 60. **Public API / evaluation security:** Raw grader records can contain stdout/stderr, candidate source, hidden-test details, gold information, commands, and other sensitive evaluator data, so exposing them through a read-only progress API can still create an exfiltration path; sanitize reports before public API exposure.
* 61. **FastAPI / Spring / Docker security:** Regression progress endpoints are intended to be read-only, and exposing a public POST endpoint that starts Docker, Maven, npm, or other execution would convert a reporting API into an execution surface; keep execution in trusted offline/CI infrastructure and expose only sanitized latest/history results.
* 62. **Regression modes:** `grader`, `software`, and `full` represent different scopes, so grader-only runs should not fail because software checks were not requested and software-only runs should not appear as 0% deterministic correctness; score and gate only checks applicable to the selected mode.
* 63. **Regression runner architecture:** Giant shell command chains terminate early and make aggregation and complete failure reporting difficult, conflicting with a deterministic report that should expose all failures; let Python handle orchestration and aggregation using subprocess argv arrays.
* 64. **Python subprocess security:** Arbitrary task/model commands must never be passed through `shell=True` because that bypasses the sandbox's command allow-list design; execute only predefined command types with explicit argv arrays.
* 65. **Sandbox command policy:** Model or task input should choose only allow-listed logical operations such as TEST or COMPILE rather than supplying arbitrary shell commands; map each trusted logical operation and language to predefined argv internally.
* 66. **Report history:** `latest.json` must be read before it is overwritten when computing a delta because otherwise the supposed previous result becomes the just-written current result; load previous → compute delta → write timestamped report → update `latest.json`.
* 67. **History API:** `latest.json` is a regression JSON file but not an independent historical run, so including it in history duplicates the newest result; exclude `latest.json` when enumerating timestamped history.
* 68. **History API:** An unrestricted caller-supplied history `limit` can trigger unnecessary filesystem and API work; clamp the maximum history size.
* 69. **Regression suite versioning:** Case-by-case delta comparisons become invalid when suite versions differ because added, removed, or renamed cases are not apples-to-apples comparisons; avoid direct changed-case comparison across different suite versions.
* 70. **UI / accessibility:** Regression state should not rely solely on red and green because color-only signaling is inaccessible and potentially ambiguous; display explicit textual states such as `PASS`, `FAIL`, statuses, and counts alongside any color.
* 71. **CI / benchmark integrity:** Intentionally changing an expected result to an incorrect value must cause CI to fail or the deterministic regression suite is merely informational; gate CI on exact deterministic expectations.
* 72. **Git / local files:** Local instruction and helper files such as `instructions.txt` can accidentally become unrelated product-source changes; ignore local-only operational artifacts that should not enter the repository.
* 73. **Docker bind mounts / read-only rootfs:** `--read-only` protects the container root filesystem but a bind mount has its own mount flags and Unix permission behavior, so it does not automatically solve `/work` ownership or accessibility; treat rootfs immutability and bind-mount permissions as separate security controls.
* 74. **Linux directory vs file permissions:** A container user requires execute (`x`) permission on directories merely to traverse them, so even readable `0644` Python files remain inaccessible behind a `0700` parent directory; ensure every parent directory in the mounted path is traversable by the sandbox UID.
* 75. **Sandbox scratch space:** Tests and compilers commonly need writable temporary/cache state even when source code should remain immutable, so making `/work` writable just to satisfy that behavior unnecessarily weakens isolation; preserve non-writable source and provide bounded writable `/tmp` tmpfs.
* 76. **Failure interpretation:** `COMPILE_FAIL`, `NO_TESTS`, `HARNESS_ERROR`, Docker `125`, Docker `127`, and actual pytest failures originate at different layers, so collapsing all of them into generic candidate failure hides the real fault domain; preserve layer-specific categories from runner through grader and regression reporting.
